# Producción de SAB en Supabase

La aplicación se ejecuta desde imágenes inmutables. PostgreSQL y los archivos de negocio viven en Supabase. Usa siempre `-f docker-compose.production.yml` para seleccionar esta pila y las imágenes por digest de una sola entrega.

## Preparación

1. Prepara un proyecto Supabase de pruebas y uno dedicado a producción con PostgreSQL 17, conexión directa y Storage privado. Configura un bucket privado, activa el endpoint S3 y guarda sus credenciales exclusivamente en el backend. Restringe el acceso a PostgreSQL a las redes de los operadores y los servidores de SAB. Verifica conectividad IPv6 directa o IPv4 dedicado desde los contenedores.
2. Desde una estación autorizada, configura `PGHOST` con el host directo, `PGUSER=postgres`, `PGSSLMODE=verify-full`, `PGSSLROOTCERT` con la CA del proyecto y `PGPASSFILE` con un fichero de modo 0600. Define las tres credenciales SAB y `DB_DATABASE=sab` en el entorno privado. Ejecuta `SAB_MANAGED_BOOTSTRAP=1 bash docker/postgres-init.sh` una vez con destino nuevo. Usa las credenciales administrativas del proyecto solo durante este paso. Si se interrumpe, inspecciona los roles y bases creados antes de reanudar.
3. Prepara los archivos a partir de [compose.env.example](compose.env.example) y [runtime.env.example](runtime.env.example). El secreto inicial de superadministrador se monta solo en el servicio `install`. Redis recibe `REDISCLI_AUTH` en su archivo privado y SAB recibe el mismo valor como `REDIS_PASSWORD`. Utiliza una cadena hexadecimal aleatoria de al menos 32 caracteres. Configura la API BCV con el mismo token en ambos servicios. Configura Centrifugo con `CENTRIFUGO_HTTP_API_KEY`, `CENTRIFUGO_CLIENT_TOKEN_HMAC_SECRET_KEY` y los orígenes HTTPS permitidos. Usa permisos de lectura para el UID del contenedor en cada secreto montado.
4. Construye los objetivos `release-php` y `release-nginx` de `docker/php.Dockerfile` desde el mismo commit. Publica las imágenes candidatas en el registro de la instalación y anota sus digests. Instala un certificado de Cloudflare Origin CA o de una CA pública que cubra el dominio raíz y el wildcard de empresas. Define `SAB_ORIGIN_CERT_FILE` y `SAB_ORIGIN_KEY_FILE` con sus rutas en el servidor. Usa en `SAB_ORIGIN_BIND_IP` la IPv4 privada de la interfaz EC2 que recibe NAT desde la IPv4 pública. Limita TCP 443 en AWS a los [rangos IPv4 oficiales de Cloudflare](https://www.cloudflare.com/ips-v4). Usa esas mismas redes en el archivo `SAB_CLOUDFLARE_REAL_IP_FILE`, una línea `set_real_ip_from CIDR;` por red. Mantén ambas listas sincronizadas. No publiques HTTP ni los puertos internos.
5. Valida la configuración con `docker compose --env-file /etc/sab/compose.env -f docker-compose.production.yml config --quiet`. Usa los mismos argumentos para `up -d redis`, `run --rm install` y `up -d php nginx worker storage-worker scheduler api-bcv centrifugo`. Ejecuta `exec php php artisan sab:check-production` y verifica `/healthz`, inicio de sesión, alta de dos empresas, archivos privados, documentos, BCV y ambas colas. Tras aprobar el candidato, apunta los registros con proxy de Cloudflare a la IPv4 pública de EC2, selecciona TLS Full (strict), redirige HTTP a HTTPS en Cloudflare y evita la caché de rutas de aplicación. Comprueba el certificado del dominio raíz y de los subdominios y la conexión WebSocket segura antes de abrir tráfico. Mantén alertas para fallos HTTP, colas, scheduler, BCV, cuota de Storage y antigüedad del último respaldo.

Para una instalación que usaba un túnel, detén únicamente el conector de SAB y verifica que Nginx pueda usar TCP 443 antes de cambiar DNS. Si la IPv4 pública de EC2 es dinámica, comprueba el registro A después de detener y volver a iniciar la instancia.

## Respaldo y recuperación

En una ventana de mantenimiento, detén los productores de escrituras y drena las colas. Ejecuta `run --name sab-db-backup maintenance sh -ec 'php artisan down && php artisan bk:bd todos --quiesced'` para crear el paquete de bases. Copia la ruta indicada a un destino privado con `docker cp` antes de retirar el contenedor. Mantén el archivo del rol de migración reservado para los servicios install y maintenance. Para archivos, usa `bk:files todos`, deja ejecutar el worker administrativo durante el respaldo y guarda una copia cifrada del ZIP publicado en el bucket. Conserva `APP_KEY` y `TENANCY_KEY` por separado. Mantén la aplicación sin tráfico de escritura durante ambos respaldos.

Ensaya la recuperación con otro proyecto, otro bucket vacío y las claves originales. Restaura la central y los tenants con `sab:restore-central` y `sab:restore-tenant` desde el paquete de bases. Extrae el ZIP individual de cada empresa del respaldo de archivos. Ejecuta `sab:restore-storage UUID RUTA` para cotejar el catálogo y luego repite con `--apply` y `SAB_STORAGE_RECOVERY=true` en el entorno de recuperación. Usa el ámbito `_system` con el ZIP global para los recursos gráficos compartidos. Comprueba autorización, documentos y adjuntos de dos empresas antes de habilitar tráfico. Conserva el candidato anterior y su compatibilidad con el esquema. Si el candidato nuevo recibió escrituras, preserva primero esas escrituras y objetos antes de cambiar de revisión.

Para publicar, verifica la ejecución de Entrega SAB del commit candidato, incluida la auditoría de dependencias de Composer. La batería completa de PostgreSQL se ejecuta aparte con `php scripts/test_postgresql.php`. El arranque conserva Laravel 10 y Vue 2 por decisión del operador. Mantén las integraciones deshabilitadas hasta acreditar su aceptación.
